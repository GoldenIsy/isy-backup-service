# On-Premise Distribution and Deployment

Status: pre-production deployment procedure

The source repository and container package are public distribution surfaces.
Customer installations do not need a GitHub account, Git credential, Personal
Access Token, Jenkins credential, or access to the source repository.

The public images are:

```text
ghcr.io/goldenisy/isy-backup-agent
ghcr.io/goldenisy/isy-installation-agent
```

Production installations must use the qualified digest supplied with their
deployment receipt. Moving tags such as `main` are for evaluation only.

## 0. Export the deployment bundle

The backup image contains the complete deployment bundle, so the customer does
not clone this repository. From an empty working directory, export it with the
qualified image digest:

```bash
mkdir -p isy-backup && cd isy-backup
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/output" \
  ghcr.io/goldenisy/isy-backup-agent@sha256:<qualified-digest> \
  deployment export --output /output
```

The command writes `compose.yml`, `config.yml`, provider examples, this README,
and `scripts/put-secret.sh`; it also creates empty `agent/` and `secrets/`
directories. It refuses to overwrite an existing deployment file.

## 1. Network requirements

The host needs outbound HTTPS to `ghcr.io` during image pull. At runtime the
container needs only DNS/time, its configured source endpoints, backup
destinations, and eventually the monitoring parent. It does not need inbound
internet access or the Docker socket.

## 2. Anonymous image pull

No registry login is required:

```bash
docker pull ghcr.io/goldenisy/isy-backup-agent:0.3.0
docker run --rm --read-only --cap-drop ALL \
  --security-opt no-new-privileges \
  ghcr.io/goldenisy/isy-backup-agent:0.3.0 version
```

The installation-agent image is selected by immutable digest through
`ISY_INSTALLATION_AGENT_IMAGE`. It contains only the outbound enrolled-agent
runtime. It receives the public bootstrap/trust files and shared control socket,
but not PostgreSQL, object-store, provider, or Restic credentials.
Both packages must pass an unauthenticated `docker manifest inspect` by digest
before an on-premise deployment receipt is issued. This catches an accidentally
private GHCR package without requiring customer registry credentials.

After qualification, replace the tag with the published immutable digest:

```text
ghcr.io/goldenisy/isy-backup-agent@sha256:<qualified-digest>
```

Set `ISY_BACKUP_IMAGE_DIGEST` to that same value. Receipts and status records
then report the deployed digest without requiring Docker-socket access.

## 3. Local directories and credentials

Create deployment-owned directories. Secret files must be readable only by
the container UID; their contents never enter Compose or Git.

```bash
sudo ./scripts/put-secret.sh restic-password
sudo ./scripts/put-secret.sh rclone.conf --from-file /path/to/rclone.conf
sudo ./scripts/put-secret.sh postgres.pgpass --from-file /path/to/postgres.pgpass
```

The first form prompts twice without placing the value in shell history or a
process argument. `--from-file` installs multi-line credentials. Existing
files are preserved unless `--replace` is stated explicitly. All installed
files are owner `1000:1000`, mode `0600`; the customer keeps the originals in
its external recovery record.

For PostgreSQL, mount an owner-only libpq password file. For pCloud, mount an
owner-only rclone configuration generated by the dedicated backup account and
an unrelated Restic repository password. The customer keeps these credentials;
neither GoldenIsy GitHub nor Jenkins requires them.

## 4. Configuration

Start from [`../config/backup-config.example.yml`](../config/backup-config.example.yml)
and add the deployment's real source and target identities. For pCloud, merge
[`../config/providers/pcloud-eu.example.yml`](../config/providers/pcloud-eu.example.yml).

Use these container paths:

```text
configuration: /etc/isy-backup/config.yml
secrets:       /run/secrets/*
state:         /var/lib/isy-backup
cache:         /var/cache/isy-backup
```

Attach the service to the application's Docker network when PostgreSQL or
MinIO is addressed by service name. Mount filesystem sources read-only.

Place the SaaS-issued public enrollment bootstrap and trust bundle at
`agent/bootstrap.json` and `agent/trust-bundles.json`. Set the three exact
installation-agent release variables shown in `compose.example.yml`, then
approve the pending registration in SaaS. The agent writes the approved public
installation UUID into the shared socket volume; no installation ID needs to
be copied into the backup configuration.

## 5. Admission and repository initialization

Before the first backup:

```bash
docker compose run --rm backup config validate --config /etc/isy-backup/config.yml
docker compose run --rm backup doctor --config /etc/isy-backup/config.yml
docker compose run --rm backup repository init \
  --config /etc/isy-backup/config.yml --target <target-id>
```

Repository initialization is explicit and performed once per target. It is
never attempted implicitly during a scheduled backup.

Apply a target's configured keep policy as an explicit maintenance operation:

```bash
docker compose run --rm backup retention \
  --config /etc/isy-backup/config.yml --target <target-id>
```

This runs Restic `forget --prune` under the deployment mutation lock and writes
a separate retention receipt. It is deliberately not a SaaS remote command.

## 6. Backup and evidence

Start the admitted long-running service with:

```bash
docker compose up -d backup backup-installation-agent
docker compose ps backup backup-installation-agent
```

The service schedules backups from the `service` configuration, emits its
heartbeat independently, and remains alive in `DEGRADED` state after a backup
failure so the parent can distinguish liveness from backup freshness. Run a
controlled one-shot backup with:

```bash
docker compose run --rm backup backup --config /etc/isy-backup/config.yml
```

Archive the emitted receipt and verify that the same receipt exists below
`/var/lib/isy-backup/receipts/`. A customer deployment is not production-ready
until readback, isolated restore, external absence detection, and Slack
failure/recovery are qualified for its exact digest and configuration.

## 7. Updates and rollback

Every push to `main` automatically publishes evaluation tags `main` and
`sha-<commit>`. A `v*` Git tag publishes the matching semantic version. The
workflow builds and tests before publishing, and uses GitHub's short-lived
repository token; no personal publishing credential is stored.

Customer deployments do not follow `main` automatically. Updates change only
the pinned image digest after that digest passes qualification. Preserve
configuration, secrets, state, and repositories. Keep the previous qualified
digest in the deployment record; rollback selects that digest and does not
delete backups or credentials.

This separation prevents an ordinary source push from silently replacing the
backup authority at every customer while still making new images immediately
available for qualification.

## 8. Slack update notifications

The external monitoring parent periodically compares each deployment's
reported digest with the newest qualified digest. It emits
`isy.backup.update-event/v1`, defined by
[`../schemas/update-event.schema.json`](../schemas/update-event.schema.json).

Alertmanager routes that event through the existing deployment-specific Slack
bridge. The notification policy is transition-based:

- one message when a newer qualified digest first becomes available;
- no routine message while the state is unchanged;
- a rate-limited reminder when the configured update window is exceeded;
- one recovery message after the deployment reports the qualified digest;
- `UNKNOWN` when the installation digest or qualified-release authority is
  missing, without guessing from a moving tag.

The backup container does not send Slack directly. A stopped container or host
must remain observable, so update and absence evaluation stays outside the
protected customer stack.
